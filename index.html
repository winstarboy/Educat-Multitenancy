Technology & AWS Architecture — Final Baseline

Recommended stack: Next.js + TypeScript for the frontend, Three.js/React Three Fiber for the public 3D experience, NestJS + TypeScript for the backend, PostgreSQL as the primary transactional database, Redis-compatible caching/queues, S3 for files, WebRTC/SFU for classrooms, and AWS for production.

BackendNestJS + TypeScriptModular monolith first, REST/WebSocket adapters, domain/application layers.
Primary DBPostgreSQL / Aurora PostgreSQLStrong fit for scheduling, finance, memberships, permissions and relational reporting.
Cache / JobsRedis-compatible + durable queuesSessions, short-lived cache, rate limits, background work and retries.
FilesAmazon S3Private objects, signed URLs, scanning, lifecycle policies and storage quotas.
RealtimeWebSocket + WebRTC/SFUChat, classroom signaling and online classes without coupling core transactions to media.
ProductionAWS + IaC + CI/CDCloudFront/WAF, ECS/Fargate or EKS later, Aurora, ElastiCache, S3, Secrets Manager/KMS, CloudWatch/OpenTelemetry.
DynamoDB recommendation: Do not make DynamoDB the primary database for this V1. It is excellent for access-pattern-driven, high-scale workloads, but this product has many relational workflows: memberships and roles, guardian relationships, enrollments, courses/levels, schedule conflicts, attendance, invoices, payments, teacher earnings and audit relationships. PostgreSQL gives you stronger relational integrity and easier querying. AWS itself recommends choosing between Aurora PostgreSQL/RDS and DynamoDB based on data model, access patterns and transactional-integrity needs.

Recommended database strategy

WorkloadRecommended storeWhy

Tenant isolation

Use a pooled PostgreSQL model initially: every tenant-owned table carries organization_id, authorization is enforced in NestJS, and PostgreSQL Row-Level Security can provide an additional database-level isolation boundary for sensitive tables. Keep a clear path to a bridge/silo model for future enterprise customers.

Next.js→CloudFront / WAF→NestJS API→PostgreSQL
　　　　　　　　　　　↘ S3 · Redis · Queue · WebSocket · WebRTC/SFU

Local development → production

  • Local: Docker Compose + LocalStack for AWS-shaped services such as S3/SQS/SNS/DynamoDB where useful, plus a real PostgreSQL container for the relational database.
  • CI: Run migrations against ephemeral PostgreSQL, integration tests against LocalStack-supported AWS services, and E2E tests against the actual application stack.
  • Staging: Use real AWS managed services rather than relying exclusively on emulators; this catches IAM, networking, signing and service-behavior differences before production.
  • Production: AWS-managed PostgreSQL/Aurora, S3, Redis-compatible cache, queues, CDN/WAF, KMS/Secrets Manager and observability.
Database decision: PostgreSQL is the default V1 system of record. If you still want DynamoDB, introduce it intentionally as a secondary store for a concrete high-throughput access pattern—not because the application is running on AWS.

32. Responsive Design System

The application should not be treated as “desktop shrunk to mobile.” Each major workflow gets an intentional mobile interaction model.

Mobile rules

  • Minimum touch target around 44px.
  • No fixed-width content.
  • Forms stack labels and controls.
  • Important actions stay reachable.
  • Dialogs become full-screen sheets where appropriate.
  • Tables become cards or prioritized columns.
  • Calendar becomes agenda/day view.
  • Filters become a bottom sheet/drawer.
  • Online classroom controls remain reachable with safe spacing.

Technical CSS rules

  • Use fluid widths and minmax() grids.
  • Use clamp() for typography.
  • Avoid viewport-fixed heights for content areas.
  • Respect env(safe-area-inset-*) on mobile.
  • Use overflow-x:auto only for genuinely tabular content.
  • Test at 320, 360, 390, 430, 768, 1024, 1280 and 1440px widths.
  • Support keyboard navigation and reduced motion.

29. Solution / Technical Architecture Deep Dive

Architecture style

Start with a modular monolith: one deployable backend with strict domain modules, plus dedicated worker processes. This is easier to operate than early microservices while preserving boundaries. Extract only proven bottlenecks such as WebRTC media, notification processing or analytics when scale demands it.

Layering rule

HTTP / WebSocket adapters
        ↓
Application services / use cases
        ↓
Domain rules + authorization policies
        ↓
Repositories / transaction boundaries
        ↓
PostgreSQL / object storage / external adapters

Controllers should not contain complex business rules. External SDKs should be hidden behind provider interfaces. Domain code should be testable without a browser or external vendor.

Critical transaction examples

  • Admin transfer: validate initiator + target → re-auth → transaction → promote target + demote initiator + write audit event → commit. Failure rolls everything back.
  • Payment webhook: verify signature → deduplicate provider event → transactionally record payment + update balance + audit → enqueue receipt. Provider retries must be safe.
  • Schedule move: lock/version-check relevant session → validate conflicts → update session → create audit event → commit → asynchronously sync Google.
  • Teacher deactivation: update membership/access state → revoke sessions → invalidate classroom authorization → audit → notify.

Domain events

Use internal events for asynchronous side effects: EnrollmentApproved, ClassScheduled, ClassRescheduled, PaymentConfirmed, TeacherDeactivated, ResourceUploaded. Store an event/outbox record in the same DB transaction as the business change, then publish it to workers. This prevents “DB updated but notification never queued” failures.

Outbox pattern

DB transaction:
  business change
  + outbox_event
        ↓ commit
Worker polls/publishes outbox
        ↓
Provider / notification / sync
        ↓
delivery status + retry / DLQ

Security boundaries

  • Tenant context is established before repository access.
  • Repository queries include tenant scope.
  • Resource authorization verifies both role and relationship.
  • File access returns signed URLs only after authorization.
  • Audit service is write-only from business code and has no update/delete API.

1. Executive Summary

Product: a configurable SaaS platform where an organization creates its branded public website and manages students, guardians, teachers, enrollments, courses, schedules, attendance, learning progress, resources, communication, online classes and student fees from one authenticated application.

First tenant: Shalom School of Music. The architecture must never hard-code “music school”; the same platform must support dance, tuition, language, sports coaching and tutoring organizations.

Core architectural rule: organization data is isolated server-side. Every tenant-owned resource carries an organizationId or is reachable only through a tenant-owned parent. The client cannot choose another tenant by changing a URL, ID or request body.

North-star quality: correctness before convenience. Financial state comes from server/webhook confirmation; authorization is server-enforced; audit events are append-only; scheduling conflicts are checked centrally; integrations are asynchronous and retryable.

Explicitly later

  • General-purpose document management
  • Payroll processing

Design principles

  1. Tenant isolation by construction.
  2. Server is authoritative. Browser results are never trusted for permissions, payments or attendance-sensitive state.
  3. History is preserved. Financial and audit records are immutable or append-only where appropriate.
  4. Integrations fail gracefully. Queues, retries, idempotency and dead-letter handling are mandatory.
  5. Configuration over code. Plans, fields, taxes, branding and limits are data-driven.
  6. Accessible responsive UX. Desktop grids transform into mobile agenda/cards instead of becoming tiny desktop layouts.

4. Roles & Access Control

RolePurposeScope
Platform Super AdminOperates the SaaS platform and support/security functions.All organizations/platform records, with audited support access.
Organization AdminRuns one organization.Full organization permissions.
TeacherRuns assigned teaching work.Own classes/students and permitted resources.
StudentConsumes learning services.Own profile, schedule, progress, resources, fees and classes.

Admin governance defaults

  • No separate Owner role.
  • Default maximum active Organization Admins: 5.
  • Organization Admin may request a higher limit; Platform Super Admin approves.
  • Plan downgrade immediately applies the new limit to additions, while existing Admins remain active.
  • Last Admin cannot simply be removed; transfer/recovery protections apply.
  • Admin transfer is two-step, expires after 7 days, one pending transfer per organization, target must re-authenticate, and transfer is atomic.
  • Admin removal/promotion/demotion requires confirmation, reason (minimum 10 characters), re-authentication and audit.
  • No bulk Admin changes in V1.
  • Admin inactivity never automatically demotes the Admin.
  • If zero Admins exist due to failure, Platform Super Admin can recover by promoting an eligible existing member after checks.

5. Authentication, Sessions & Account Security

Login methods

  • Email + password
  • Phone + OTP
  • Google login

Google Calendar OAuth is separate from Google login.

MFA

  • Super Admin: mandatory
  • Organization Admin: mandatory
  • Teacher: optional
  • Student: optional
  • Parent/Guardian: optional

V1: authenticator-app TOTP + recovery codes. MFA is distinct from phone OTP login.

Session controls

  • View/revoke individual sessions.
  • Revoke all other sessions.
  • Password change revokes other sessions.
  • MFA changes revoke other sessions.
  • Major security events create email + in-app alerts.
  • Progressive temporary lockout + rate limiting after failures.

Account recovery

  • Normal users who lose both email and phone: Admin-assisted identity verification.
  • Organization Admin recovery: Platform Super Admin approval after identity verification.
  • Platform Super Admin recovery: dedicated break-glass process outside normal app, multiple independent verification factors, full audit and notification.
  • Email/phone changes require re-authentication, new-contact verification, session revocation and security notification.

6. Organizations, Branding & Tenant Isolation

Organization profile

Name, logo, website, description, contact details, address, timezone, country, currency, brand colors, branches, courses, public-site configuration and subscription/entitlements.

Tenant isolation diagram

End-to-end logical architecture

Public website

7. Students, Guardians & Enrollment

Student model

  • Standard profile: name, DOB, gender, email, phone, address, profile photo.
  • Emergency contact: name, phone, relationship.
  • Organization-specific custom fields: Text, Number, Date, Dropdown, Multi-select, Checkbox, URL.
  • Custom fields are configuration-driven and support per-field visibility.
  • DOB determines whether guardian details are required using an organization-configurable adult threshold.

Guardians

  • Many-to-many student ↔ guardian.
  • Multiple guardians have equal status; no primary guardian.
  • One guardian account may manage multiple children.
  • Any linked guardian can pay.
  • Payments attach to the student/fee, while payer identity is stored in payment history.

Enrollment lifecycle

INVITED → APPLICATION_SUBMITTED → UNDER_REVIEW → APPROVED → ACTIVE
                              ↘ REJECTED
ACTIVE → CANCELLED / INACTIVE

Teacher signup flow

Teacher sends a tokenized enrollment link. The link identifies the intended teacher/enrollment context but grants no dashboard access. Student/parent submits details; teacher approves; then the enrollment becomes active according to the organization's rules.

Tenant isolation defense in depth

8. Teachers

  • Employment types: Full-time, Part-time, Contract, Freelancer.
  • Soft deactivation only in V1; no physical deletion.
  • Deactivation immediately revokes org access, sessions, API/WebSocket/classroom access.
  • Reactivation restores normal login with existing credentials.
  • Admin-managed teaching capabilities: course + optional level; explicit assignment required for new courses/levels.
  • Capabilities do not expire automatically.
  • Capacity is checked using both maximum active students and available teaching hours.
  • Admin can override capacity/conflict with reason and audit.
  • Teacher custom fields use the same flexible field system as students.
  • Structured qualifications/certifications and private documents are supported.
  • Teacher can edit own permitted profile fields; Admin controls sensitive/employment fields.
  • Public profile is optional, uses explicitly public-enabled fields, and teacher edits require Admin approval before publication.
  • Inactive teachers are hidden publicly by default, with Admin override.
Teacher/student access is relationship-based through Enrollment/Learning Program, not a direct “teacher owns student” link. This supports multiple teachers, courses and branches for one student.

11. WebRTC Online Classroom

The platform owns the classroom UX and uses WebRTC. For reliability and multi-participant scaling, use an SFU/media-server layer rather than pure browser-to-browser mesh.

Conflict detection flow

Classroom requirements

  • Camera, microphone, screen share.
  • Chat.
  • Recording controlled by teacher.
  • Option “Record this class”.
  • Option “Share recording with student”.
  • Authenticated private rooms.
  • Reconnection and network-quality adaptation.
  • Echo/noise handling using browser capabilities and server-side monitoring where applicable.
  • STUN/TURN for difficult networks.
  • Recording storage and retention must be quota/plan-aware.
Important implementation note: “Build our own classroom” should mean owning the application, authorization, UX and orchestration. Reusing mature open-source media infrastructure such as an SFU/TURN implementation is safer than implementing RTP/media routing from scratch.

12. Learning Resources & File Storage

Resource scopes: organization library, student/enrollment library and class-specific resources. Examples include sheet music, PDFs, books, videos, documents and links.

  • DB stores metadata; object storage stores bytes.
  • Upload progress.
  • File size/type limits and plan quotas.
  • Private storage with short-lived signed URLs.
  • Malware scanning before making a file available.
  • Download/stream permissions.
  • Shared organization library reduces duplicate uploads.

13. Messaging, Notifications & WhatsApp

Native messaging is the core channel

  • Teacher ↔ student/parent.
  • Admin ↔ anyone in organization.
  • Class-specific conversations.
  • Announcements.
  • Attachments: images, PDFs, videos and links.
  • Read/unread state and notifications.
  • Class reminders, fee reminders and system messages.

Provider-agnostic notification model

APP | EMAIL | WHATSAPP | WHATSAPP_GROUP | PUSH

Every notification should have a durable event ID, template/version, recipient, channel, status, retry count and provider message ID where available.

WhatsApp constraint: production automation must use official/compliant WhatsApp Business infrastructure and applicable consent/template/pricing rules. Do not use WhatsApp Web browser automation, QR-session bots, Puppeteer/Playwright hacks or unofficial APIs. The exact ability to post into arbitrary existing personal WhatsApp groups must be verified against the official product capability before promising it.

The product should therefore keep native messaging as a first-class fallback. If an official group-posting capability becomes available and is authorized for the tenant, implement it behind the WHATSAPP_GROUP provider adapter.

14. Student Finance

Fee and payment rules

  • One-time and periodic fees.
  • Partial or full payments.
  • Multiple guardians can pay the same student's balance.
  • Payment belongs to the student/fee record; payer is recorded separately.
  • Payment success is confirmed by gateway webhook/server verification, never only by browser redirect.
  • Gateway interface is abstracted so provider can change later.
  • Refunds are planned as a supported transaction type; original payment remains in history.

Teacher earnings

  • Fixed amount per completed class OR percentage of student revenue.
  • Can vary by teacher/course.
  • Calculated from completed classes/revenue according to configured rules.
  • No payroll processing in V1.

Discounts / scholarships

  • Fixed or percentage.
  • Teacher may request/apply subject to Admin approval.
  • Reason, requester, approver and dates retained.
  • Original and final amounts retained.

Tax

  • Organization-configurable tax enabled/name/rate/inclusive setting.
  • Historical invoices store the tax context used at issuance so future setting changes do not change history.
  • Organization has one default currency; currency is also stored on financial records.

Invoice + receipt

Invoice number, student, enrollment/course, fee lines, discount, tax, amount paid, balance, method, gateway reference, payment date and organization branding. Both invoice and payment receipt are generated as PDF/shareable artifacts.

15. SaaS Billing, Plans & Entitlements

Plan model

Support Trial, Starter, Growth, Professional and Enterprise/custom. Exact prices are commercial configuration, not business logic.

Entitlement architecture

Plan → Entitlements → Organization Overrides → Usage Enforcement

Typical entitlements: maxTeachers, maxStudents, storageGB, monthlyOnlineMinutes, recordingStorageGB, feature flags.

Lifecycle

TRIAL → ACTIVE → GRACE_PERIOD → RESTRICTED → SUSPENDED → DELETED
  • Trial default: 14 days.
  • Cancellation retains access until current billing period ends.
  • Afterward restricted/read-only, then suspended if applicable.
  • Data is preserved according to plan retention.
  • Organization deletion requires Admin request + Platform Super Admin confirmation.
  • Monthly, yearly and custom/enterprise billing supported.
  • Plan upgrade does not automatically increase organization Admin limit.
  • Downgrade: existing Admins remain, but new Admin additions are blocked above the new limit.

18. Data Model

Critical entity rules

  • Use immutable IDs such as UUID/ULID.
  • All tenant-owned tables include organization_id unless ownership is unambiguously inherited through a tenant-owned parent; denormalizing it onto high-volume tables is recommended for safer filtering and indexing.
  • Foreign keys enforce relationships.
  • Unique constraints prevent duplicate memberships/invitations and other business duplicates.
  • Soft deletion/deactivation is used where history matters; never hard-delete financial/audit history.
  • Money uses integer minor units or fixed-precision decimal, never floating point.
  • All financial rows store currency code.
  • All timestamps stored UTC.

19. Security Architecture

Mandatory controls

  • HTTPS everywhere; secure cookies where cookies are used.
  • CSRF protection for cookie-authenticated state-changing requests.
  • Strict CORS allowlist.
  • Content Security Policy and security headers.
  • Password hashing with Argon2id or a maintained equivalent.
  • OTP expiry, one-time use and attempt limits.
  • Rate limiting on login, OTP, password reset, invitations and sensitive endpoints.
  • Server-side authorization on every protected resource.
  • Secrets only in secret management systems, never source control.
  • Encryption at rest and in transit.
  • File scanning and content-type validation.
  • Parameterized DB access / ORM protections.
  • Dependency scanning, SAST, secret scanning and container scanning in CI.
  • Security event notifications and suspicious-login detection.
Never put secrets in frontend code. Payment secret keys, database credentials, OAuth client secrets, TURN credentials and encryption keys belong server-side or in a managed secret system.

20. Audit, Security Logging & Integrity

Retention and access

  • Core audit retention: 7 years.
  • Organization Admins see only their organization's logs.
  • Platform Super Admin sees platform-wide logs.
  • CSV export is async with a temporary signed URL expiring after 1 hour.
  • Generated export files are deleted within 24 hours after link expiry.
  • Default export limit: 100,000 records, configurable.
  • Security-sensitive export requires separate permission.

Never store passwords, MFA secrets, access tokens, refresh tokens or encryption keys.

Integrity model

  • One chain per organization plus a separate platform-level chain.
  • Daily integrity checkpoints.
  • Critical events trigger immediate external checkpoint.
  • Automatic daily verification.
  • Verification failure → forensic external checkpoint, alert Platform Super Admin, mark chain compromised, preserve evidence.
  • Organization Admin sees a security warning but not sensitive investigation details.
  • Compromised chain is permanently marked compromised and frozen; a new chain begins.
  • Manual verification available to Platform Super Admin and authorized Organization Admin for their own org; verification itself is audited.
  • External checkpoints use immutable cloud WORM + third-party tamper-proof integrity service.
  • Audit encryption: platform KMS for normal plans; customer-managed keys for Enterprise.
  • Only security/infrastructure service accounts can access encryption keys.
  • Automatic KMS key rotation; historical rows retain key-version references.
  • India data residency by default; Enterprise regional selection later.
  • Encrypted + immutable backups retained 7 years.

21. Integrations

Google Calendar

  • Platform calendar is source of truth.
  • User connects Google Calendar through separate OAuth.
  • Adult student connects own calendar.
  • Child's guardian account can connect.
  • Connected users receive automatic event create/update/cancel.
  • Disconnected users receive calendar invitation or .ics fallback.
  • Updates modify the existing external event using stored external event ID; never create duplicates.
  • Sync jobs are idempotent and retryable.

Payment gateway

Use an adapter interface such as PaymentProvider.createIntent(), verifyWebhook(), refund(). Business logic must depend on the interface, not a provider SDK directly.

WhatsApp

Implement a provider adapter. Keep compliance, opt-in, templates, message-window rules and provider capability checks outside core messaging logic.

22. Reliability, Observability & Failure Handling

Required practices

  • Structured JSON logs.
  • Correlation/request ID on every relevant request and audit event.
  • Metrics: latency, error rate, queue depth, job retries, payment webhook failures, calendar sync failures, classroom connection quality, storage usage.
  • Distributed tracing across API → DB → queue → provider → audit where feasible.
  • Timeouts on external calls.
  • Retries only for transient failures with exponential backoff and jitter.
  • Dead-letter queues for exhausted jobs.
  • Idempotency keys for financial/integration operations.
  • Health/readiness endpoints.
  • Graceful shutdown for workers.

Availability philosophy

Core operations must not depend synchronously on non-critical third parties. Example: creating a class succeeds even if Google Calendar is temporarily unavailable; calendar sync becomes “pending/retry”.

23. Deployment & Environment Architecture

Environments

  • Local development.
  • Shared development/integration.
  • Staging: production-like data shapes, synthetic/test data only.
  • Production: protected deployments and separate credentials.

Production baseline

  • Managed PostgreSQL with automated backups and point-in-time recovery.
  • Redis-compatible store for caching/rate limiting/queues where appropriate.
  • Private object storage with lifecycle policies.
  • CDN/WAF in front of public assets and APIs as appropriate.
  • Secrets manager/KMS.
  • Separate worker processes.
  • SFU/TURN infrastructure for classroom.
  • Infrastructure-as-code once environments stabilize.

The URL can contain an organization identifier for navigation, but the server must verify it matches the authenticated membership. An attacker must not gain cross-tenant access by changing orgId.

API rules

  • Consistent response/error envelope.
  • Pagination for lists.
  • Filtering/sorting with allowlists.
  • Optimistic concurrency/version field for mutable resources.
  • Idempotency keys for operations that create financial or external side effects.
  • Request validation at the API boundary.
  • Authorization after authentication and before data access.
  • Never expose internal stack traces or secrets.
  • OpenAPI contract generated/maintained as part of the build.

Non-negotiable security tests

  • Every protected endpoint tested with another organization's ID.
  • Teacher cannot access unrelated student's private fields.
  • Guardian cannot access another child's data.
  • Admin permissions cannot be self-granted.
  • Last-Admin protection cannot be bypassed.
  • Payment redirect alone cannot mark payment successful.

  • Deactivated teacher loses sessions and classroom access.

Definition of “bulletproof”

No software system can honestly guarantee zero defects. In this blueprint, bulletproof means the architecture deliberately reduces the highest-impact failure modes: cross-tenant data leakage, privilege escalation, duplicate financial effects, lost history, integration outages, unauthorized files, stale Admin transfers, and untraceable security events.

Recommended build order: do not start with the public Three.js experience or video classroom. Build identity, tenancy, authorization, data boundaries, audit and core domain models first. Everything else becomes safer and easier once those foundations are correct.
